# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

Новые маршруты для периодических задач:

- `POST /api/v1/task-templates` - Создать шаблон периодической задачи
- `GET /api/v1/task-templates` - Получить список шаблонов
- `GET /api/v1/task-templates/{id}` - Получить шаблон по ID
- `PUT /api/v1/task-templates/{id}` - Обновить шаблон
- `DELETE /api/v1/task-templates/{id}` - Удалить шаблон
- `POST /api/v1/task-templates/generate` - Для тестирования: Запустить логику воркера на конкретную дату
- `POST /api/v1/task-templates/run-worker` - Для тестирования: Ручной запуск логики которая работает автоматически в полночь
- `POST /api/v1/task-templates/force-advance` - Для тестирования: Сдвигает ВСЕ задачи на следующую подходящую дату БЕЗ ЛЮБЫХ ПРОВЕРОК

**Важно**: Эндпоинты помеченные как "Для тестирования" должны быть доступны ТОЛЬКО администраторам. На продакшн сервере обычные пользователи не должны иметь к ним доступ. Эндпоинт `force-advance` рекомендуется вообще убрать из роутера на проде.

## Архитектурные решения

### 1. Разделение на Шаблоны и Экземпляры задач

Было принято принципиальное решение не генерировать задачи на много дней вперед. Вместо этого существует только одна актуальная задача на шаблон.
- **TaskTemplate** - хранит правило периодичности, заголовок, описание и дату последней генерации
- **Task** - конкретная задача на определенный день, сгенерированная из шаблона

Обоснование:
- В 99% случаев пользователю нужна только ближайшая задача. Задачи на месяц вперед это только лишний мусор в БД
- При изменении правила периодичности не нужно обновлять тысячи уже созданных задач
- Нет проблемы рассинхронизации при изменении шаблона
- В десятки раз меньше нагрузки на базу данных

### 2. Логика обработки повторяющихся задач

Это самое важное решение в проекте:
При обработке задач в полночь:
- Если задача выполнена (`done`) - **создается новая задача** на следующую подходящую дату
- Если задача НЕ выполнена (`new/in_progress`) - **существующая задача переносится** на следующую дату

Обоснование:
Пользователи не хотят видеть пачку одинаковых невыполненных задач за вчера, позавчера и т.д. Если врач не сделал обход пациентов в понедельник, он не получит во вторник новую задачу, вместо этого та же самая задача просто перенесется у него на вторник. 

### 3. Расчет следующей даты

Следующая дата всегда вычисляется **относительно последней плановой даты задачи**, а не относительно даты запуска воркера.

Обоснование:
Даже если воркер не работал неделю, при запуске интервалы не сдвинутся, система просто догонит пропущенные шаги и все даты останутся на своих местах согласно правилу периодичности. Это гарантирует строгое соблюдение интервалов независимо от простоев системы.

### 4. Идемпотентность

Добавлен уникальный индекс `UNIQUE(template_id, scheduled_date)` в таблице tasks.

Обоснование:
Гарантирует что для одного шаблона никогда не будет создано две одинаковые задачи на один день. Даже если воркер запустится 10 раз подряд, дубликатов никогда не появится.

### 5. Разделение логики ручного и автоматического воркера

Два разных режима работы:
Автоматический воркер (полночь) - делает ровно один шаг за раз
Ручной эндпоинт `/generate?date=X` - перепрыгивает сразу все промежуточные шаги до запрошенной даты

Обоснование:
Для администратора при тестировании не имеет смысла ждать полуночи чтобы протестировать работоспособность воркера. Для автоматического режима наоборот важно сделать ровно один шаг за раз.

### 6. Обработка выполненных задач

Даже если при обновлении статуса существующей задачи, пользователь забудет указать поле `scheduled_date` задачи система все равно сможет посчитать следующую дату, используя `last_generated_date` из шаблона.

Обоснование:
Никогда не должно быть ситуации когда неправильно обновленная задача блокирует генерацию следующих экземпляров.

### 7. Граничные случаи

Реализована обработка следующих граничных случаев:
- **31 число месяца**: Если запрошено создание задачи 31 числа, а в текущем месяце меньше дней, задача создается в последний день месяца
- **Четные/нечетные дни**: Корректная обработка для любых месяцев включая февраль
- **Дата окончания**: Ни одна задача никогда не будет создана после указанной даты окончания шаблона
- **Дата в прошлом**: При создании шаблона с датой в прошлом система автоматически пропускает все прошедшие даты и создает задачу на ближайшую подходящую дату в будущем или настоящем
- **Часовые пояса**: Все вычисления происходят строго в UTC без смещений



## Примеры запросов

Ниже приведены полные рабочие примеры для всех поддерживаемых типов периодичности.

---

### Ежедневные задачи (каждый N-й день)
Создает задачу которая будет повторяться через каждые `interval` дней:
```json
POST /api/v1/task-templates
{
  "title": "Обход пациентов",
  "description": "Обойти всех пациентов отделения",
  "recurrence_type": "daily",
  "recurrence_params": {
    "interval": 3
  },
  "start_date": "2026-04-09",
  "end_date": "2026-12-31"
}
```
Параметр `interval` может быть от 1 до 365

---

### Ежемесячные задачи на определенные числа
Создает задачу которая появляется каждый месяц в указанные числа:
```json
POST /api/v1/task-templates
{
  "title": "Месячный отчет",
  "description": "Подготовить месячный отчет по работе отделения",
  "recurrence_type": "monthly",
  "recurrence_params": {
    "days": [10, 20, 31]
  },
  "start_date": "2026-04-09",
  "end_date": "2026-12-31"
}
```
Если указанного числа нет в месяце (например 31 февраля), задача создастся в последний день месяца

---

### Задачи на конкретные даты
Создает задачу которая появится только в указанные даты:
```json
POST /api/v1/task-templates
{
  "title": "Плановая аттестация персонала",
  "description": "Провести аттестацию врачей отделения",
  "recurrence_type": "specific_dates",
  "recurrence_params": {
    "dates": ["2026-05-15", "2026-08-20", "2026-11-10"]
  },
  "start_date": "2026-04-09",
  "end_date": "2026-12-31"
}
```
Даты указываются в формате `YYYY-MM-DD`, даты в прошлом автоматически игнорируются

---

### Задачи на четные/нечетные дни
Создает задачу которая появляется только в четные или только в нечетные дни месяца:
```json
POST /api/v1/task-templates
{
  "title": "Формирование отчетности",
  "description": "Сформировать дневную отчетность",
  "recurrence_type": "even_odd",
  "recurrence_params": {
    "type": "odd"
  },
  "start_date": "2026-04-09",
  "end_date": "2026-12-31"
}
```
Допустимые значения `type`: `even` (четные дни) или `odd` (нечетные дни)

---

### Ручной запуск генерации задач
Для тестирования можно запустить логику воркера на любую произвольную дату:
```json
POST /api/v1/task-templates/generate
{
  "date": "2026-05-10"
}
```
Система пропустит все промежуточные шаги и сразу переместит задачи на ближайшую подходящую дату после указанной

---

### Ручной запуск автоматического воркера
Запустит точно такую же логику которая запускается автоматически каждый день в полночь:
```bash
POST /api/v1/task-templates/run-worker
```
